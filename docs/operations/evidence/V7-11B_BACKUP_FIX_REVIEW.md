## Risques résiduels

- **P2 — durabilité du nom du backup.** Le fd est synchronisé (`backend/atlas_backend/store.py:345-346`), mais le répertoire parent ne l'est pas. Après une coupure brutale, la persistance du contenu ne garantit pas à elle seule celle de l'entrée de répertoire.
- **P2 — concurrence sur le répertoire et frontière du snapshot.** `O_EXCL`/`O_NOFOLLOW` ferment la course entre le premier `lstat` et la création. Le contrôle du nom et de l'inode (`backend/atlas_backend/store.py:348-359`) précède la relecture ; le chemin n'est pas contrôlé une dernière fois juste avant de rendre la main à la migration. Un processus pouvant modifier le répertoire pourrait remplacer/supprimer le nom après le contrôle. En outre, le snapshot (`backend/atlas_backend/store.py:327-337`) et le `BEGIN IMMEDIATE` de migration (`backend/atlas_backend/store.py:264-266`) sont séparés : la procédure doit garantir l'arrêt des écrivains pendant toute cette fenêtre.
- **P2 — mémoire proportionnelle à la base.** La base entière est copiée en mémoire puis sérialisée ; la relecture accumule aussi les blocs avant leur concaténation (`backend/atlas_backend/store.py:327-339,364-384`). Une base devenue volumineuse peut faire échouer le démarrage par pression mémoire.
- **P2 — erreur de fermeture non normalisée.** `os.close` est exécuté dans le `finally` en dehors du bloc de conversion (`backend/atlas_backend/store.py:394-415`). Son échec peut sortir du helper comme `OSError` brute ; le démarrage échoue fermé, mais le contrat d'erreur n'est pas uniforme.
- **P3 — portabilité.** `O_NOFOLLOW`, `pread` et les API SQLite `serialize`/`deserialize` dépendent de la plateforme et de la compilation Python/SQLite (`backend/atlas_backend/store.py:306-307,367-368,383-384`). Les environnements non compatibles échoueront fermé ; la preuve B7 indique Python 3.12 mais ne documente pas de matrice de plateformes (`docs/operations/evidence/V7-11B_BACKUP_PERMISSIONS_FIX_EVIDENCE.md:30-35`).
- **P2 — démarrage si un ancien backup est présent.** Si le fichier préexistant en mode `0644` signalé, d'environ `64 K`, se trouve à côté de la base à migrer, le code refusera volontairement la migration et l'initialisation du nouveau Core échouera avant le schéma V4. La localisation actuelle de ce fichier n'a pas été vérifiée. Il faut l'inspecter puis le déplacer dans une fenêtre autorisée, sans le remplacer silencieusement (`docs/operations/evidence/V7-11B_BACKUP_PERMISSIONS_FIX_EVIDENCE.md:9,37-40`).

## Conditions avant toute action live

1. Inspecter et déplacer l'ancien backup s'il est présent ; confirmer l'absence du chemin avant démarrage, puis vérifier mode `0600`, propriétaire, intégrité et version du nouveau backup.
2. Rejouer la migration corrigée sur une copie vérifiée avec le SHA final, car la migration de copie B5 précède ce correctif. Conserver une sauvegarde/restauration testée.
3. Obtenir une fenêtre de sauvegarde autorisée : arrêt du Core et du connecteur, snapshots Core/Relay/connecteur (les trois fichiers d'état) et Pixel, avec restauration vérifiée (`docs/operations/V7-11B_PREPARATION.md:188-189,218-219`).
4. Obtenir une autorisation distincte et nominative pour migrer la base live. Le Relay doit être administrable et sa recréation testée hors live ; le backup connecteur doit inclure l'état manquant documenté (`docs/operations/V7-11B_PREPARATION.md:191-193`).
5. Décider explicitement du traitement des propositions sans propriétaire et de la proposition en attente d'expiration avant tout backfill ou rapprochement (`docs/operations/V7-11B_PREPARATION.md:220-221`).
6. Après migration seulement, vérifier le principal et son association au connecteur. Aucun import d'identifiant d'accès, changement de credential, APPLY, révocation ou rotation sans autorisation spécifique (`docs/operations/V7-11B_PREPARATION.md:222-223,193`).
