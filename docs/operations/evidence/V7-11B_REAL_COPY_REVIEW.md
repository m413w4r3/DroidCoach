## Findings

### P1 — Le code ne garantit pas des permissions restrictives pour le backup automatique

`_create_coherent_pre_migration_backup` crée le fichier avec `sqlite3.connect(backup_path)` sans création exclusive, mode 0600 explicite ni vérification de permissions (`store.py`, lignes 283–297). Les permissions dépendent donc de l’umask et des droits du répertoire. Dans la preuve B5, le `chmod 600` est exécuté manuellement après l’initialisation (lignes 99–106) et la copie se trouvait dans un répertoire privé ; cela sécurise cette copie, mais ne démontre pas que le chemin d’initialisation utilisé par un service live protège son backup. Un backup SQLite peut contenir des propositions et des données d’authentification hachées. **Avant toute migration live, le code ou le runbook doit garantir et vérifier le mode restrictif avant de considérer le backup utilisable.**

### P2 — Un backup préexistant est accepté sans preuve de correspondance

Si `.pre-v4.bak` existe déjà, le code vérifie uniquement `integrity_check` puis le réutilise ; il ne contrôle ni sa version, ni son ledger, ni sa correspondance avec la source, ni son mode (lignes 286–292). Un backup SQLite intègre mais ancien ou issu d’une autre base pourrait donc être pris pour la sauvegarde pré-migration. B5 rapporte un backup v3 cohérent pour son exécution ; le chemin avec backup préexistant n’est pas couvert par cette preuve. Vérifier l’identité du backup et sa version avant réutilisation, ou refuser de continuer si sa provenance n’est pas établie.

### P2 — Chaque réouverture déclenche une transaction d’écriture sans migration en attente

L’initialiseur ouvre une transaction immédiate et réécrit `user_version` pour les versions déjà présentes à chaque démarrage (`store.py`, lignes 258–281). B5 constate un hash binaire différent malgré un dump SQL logique stable (preuve, lignes 131–133). Cela ne modifie pas la sémantique SQLite, mais peut provoquer des écritures et contentions inutiles, et invalider des comparaisons binaires ou des alertes de hash. Ne sauter les migrations déjà appliquées que si le ledger et `user_version` sont cohérents.

### P2 — Le registre conserve des UUID de sessions d’agents

Le registre contient des identifiants d’orchestration complets et abrégés (lignes 49 et 76–80). Aucun identifiant de base, d’appareil ou secret n’a été trouvé dans les éléments de B5, mais les UUID de sessions ne sont pas nécessaires à la preuve technique ; leur présence est déjà identifiée dans B4. Réduire ces valeurs à des rôles ou à des références non réversibles dans les prochains rapports.

## Limites et recommandation

- Cette revue n’a pas interrogé Docker, le live, ADB, ni un appareil. Aucun test, migration, backup ou restore n’a été exécuté.
- Les exports, le backup et la copie B5 ont été supprimés ; leurs hashes et sorties sont examinés comme preuves fournies, pas recalculés.
- La preuve B2 ne contient pas de hash de snapshot permettant une comparaison binaire avec les exports B5.
- Le verdict local valide le scénario documenté sur une copie privée. Les points P1/P2 portent sur la robustesse du chemin général de migration et sur la traçabilité documentaire.

**Recommandation :** conserver `GO_V7_11_REAL_COPY_MIGRATION` uniquement pour l’essai local documenté et maintenir `GO_V7_11_LIVE_CHANGE_READINESS` à **NO-GO**. Avant de réexaminer le live, garantir les permissions et l’identité/version du backup pré-migration, puis soumettre le code et les preuves à une nouvelle revue. Cette recommandation n’autorise aucune action sur le live.
