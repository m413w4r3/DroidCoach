## Objectif observable

Ajouter un endpoint authentifié `POST /v3/agent/plan-revision` qui demande au
planificateur OpenClaw une proposition `plan.revise_day`, la valide strictement
avec `plan_v3.py`, la retourne dans l'enveloppe `PlanProposalEnvelopeV3`, et
garantit l'idempotence durable. **Aucune exécution, aucun effet calendrier,
aucun outil exposé au planificateur.**

## Contrat de requête (gelé)

`PlanRevisionRequestV3` (`extra="forbid"`, strict) :

```json
{
  "schema_version": 3,
  "request_id": "<uuid>",
  "conversation_id": "<string|null>",
  "message": "<1..2000>",
  "plan_context_consented": true,
  "mandate_summary": { "...MandateSummary existant..." },
  "plan": {
    "plan_id": "<uuid>",
    "local_date": "YYYY-MM-DD",
    "timezone": "Europe/Paris",
    "version": 3,
    "state": "DRAFT|APPROVED",
    "activities": [
      {
        "activity_id": "<uuid>",
        "kind": "FOCUS|TRAINING|APPOINTMENT|ADMIN|MEAL|REST|BUFFER|OTHER",
        "title": "<1..80>",
        "start_minute": 540,
        "duration_minutes": 50,
        "priority": "REQUIRED|IMPORTANT|OPTIONAL",
        "goal_id": "<uuid|null>"
      }
    ]
  }
}
```

Règles :
- `plan_context_consented` faux → **403**, adaptateur non appelé.
- `plan.activities` ≤ 32, bornes 0..1439 / 1..1440, titres sans caractère de
  contrôle, ids UUID uniques.
- Le backend ne fait qu'une **pré-validation** (`validate_plan_revision`) :
  `plan_id`, `base_version == plan.version`, `activity_id` connus, expiration.
  Android revalidera tout.

## Contrat de réponse (gelé)

```json
{
  "schema_version": 3,
  "reply": "<string>",
  "agent_status": "ok|unavailable|invalid_output|quota_limited",
  "proposal": <PlanProposalEnvelopeV3|null>,
  "overlaps": [["client_ref-a", "client_ref-b"]]
}
```

- `proposal.proposal.parameters` provient du modèle, validé strictement.
- `proposal_id`, `idempotency_key`, `created_at`, `expires_at` sont générés par
  le backend (TTL 24 h par défaut), jamais par le modèle.
- Si le modèle produit un JSON invalide, un champ inconnu, ou une proposition
  incohérente : `proposal = null`, `agent_status = "invalid_output"`, HTTP 200
  avec un `reply` explicite ; aucune exception non contrôlée.
- Si l'adaptateur est indisponible : HTTP 503, `proposal = null`,
  `agent_status = "unavailable"`.

## Idempotence durable

- Clé = `request_id` + SHA-256 canonique du corps (hors champs volatils).
- Même `request_id` + même corps → même réponse, adaptateur appelé **une seule
  fois**.
- Même `request_id` + corps différent → **409**.
- Persistance SQLite atomique ; un crash entre appel modèle et écriture ne doit
  pas produire une seconde proposition au retry.

## Adaptateur OpenClaw

- Nouvelle méthode `propose_plan_revision(...)` dans `openclaw_adapter.py`.
- System prompt dédié : sortie JSON stricte
  `{"reply": string, "proposal": {"action_type":"plan.revise_day","reason":...,"parameters":...} | null}`.
- **Aucun outil** dans la requête (aucun champ `tools`), le planificateur reste
  sans capacité d'exécution. Le test doit inspecter le payload envoyé.
- Payload borné par `ATLAS_AGENT_MAX_PAYLOAD_BYTES` existant.
- Aucune donnée secrète dans le prompt ou les logs. Le contexte plan est la
  seule donnée personnelle, et il est consenti par l'UI.

## Oracle discriminant

```bash
cd backend && .venv/bin/python -m pytest -q tests/test_plan_agent_v3.py
cd backend && .venv/bin/python -m pytest -q
```

Tests minimaux :
1. requête valide → enveloppe conforme, champs générés côté serveur ;
2. `plan_context_consented=false` → 403, adaptateur non appelé ;
3. `base_version` périmée → proposition nulle, raison explicite ;
4. `activity_id` inconnu → rejet ;
5. chevauchements signalés sans être supprimés ;
6. adaptateur indisponible → 503 ;
7. sortie modèle invalide → `invalid_output`, pas de 500 ;
8. même `request_id` + même corps → même proposition, un seul appel ;
9. même `request_id` + corps différent → 409 ;
10. aucun `tools` dans le payload adaptateur ;
11. champs inconnus → 422 ;
12. expiration respectée.
