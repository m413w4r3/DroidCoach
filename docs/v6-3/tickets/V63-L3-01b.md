## Objectif observable

Recevoir une proposition `plan.revise_day` (enveloppe V3), la parser
strictement, la convertir en activités `DayPlan`, produire le diff avant/après,
et la soumettre au flux de prévisualisation + confirmation groupée existant.
**Aucune application sans confirmation ; aucun effet hors du diff confirmé.**

## Règles de parsing

- `schema_version == 3`, `action_type == "plan.revise_day"`, `state == "proposed"`,
  `required_level == "confirm"`.
- Champs inconnus, nuls non autorisés, types incorrects, UUID non canoniques,
  dates invalides, timezone inconnue, `client_ref` dupliqué, `activity_id`
  dupliqué, activité sur une autre date/timezone, total > 1440 min, > 32
  activités → rejet explicite, aucune exception non contrôlée.
- `expires_at > created_at`, TTL ≤ 24 h.
- `focus` ou `training_ref` non nuls → rejet `UNSUPPORTED_PROPOSAL_FIELD`
  (le modèle Android `PlanActivity` ne les porte pas encore ; aucun drop
  silencieux).

## Mapping vers `PlanActivity`

- `activity_id` non nul : l'activité doit exister dans le plan courant et
  partager `planId`/date/timezone. Conserver `status`, `createdRevisionId`,
  `actualMinutes` et `estimateMinutes` existants ; remplacer `kind`, `title`,
  `start_minute`, `duration_minutes`, `priority`, `goal_id`, `sub_goal_id`,
  `notes`.
- `activity_id` nul : nouvelle activité avec un UUID **déterministe** :
  `UUID.nameUUIDFromBytes("$planId:$clientRef:$baseVersion")` ; statut
  `PLANNED` ; `createdRevisionId`/`lastRevisionId` = revision id.
- L'`activity_id` de révision est **déterministe** depuis `proposal_id` :
  `UUID.nameUUIDFromBytes("plan-revision:$proposalId")`, afin qu'un rejeu de la
  même enveloppe produise la même révision et un no-op idempotent.
- `summary` = `parameters.summary` ; `origin = AGENT`.

## Contrôles avant prévisualisation

- Plan courant chargé ; `plan_id`, `local_date`, `timezone` identiques ;
  `base_version == plan.version` ; `expires_at > now`.
- Sinon message explicite : `PLAN_MISMATCH`, `STALE_AGENT_REVISION`,
  `AGENT_REVISION_EXPIRED`.
- `PlanRevisionEngine.createRevision` puis `DayPlanRepository.preview` : le diff
  et le `scope_hash` existants couvrent le contenu avant/après.
- `confirmPreview` existant applique exactement l'ensemble confirmé ; rejeu →
  `AlreadyApplied`.

## Client HTTP

- `PlanRevisionApiClient`: `POST {baseUrl}/v3/agent/plan-revision`, Bearer,
  `Content-Type: application/json`, timeouts bornés (connexion 4 s, lecture
  65 s), taille de réponse bornée, aucun log de token ou de corps personnel.
- Corps : `schema_version=3`, `request_id` stable, `conversation_id`, `message`,
  `plan_context_consented=true`, `mandate_summary`, `plan` (plan_id, date,
  timezone, version, state, activités minimisées : id, kind, title, start,
  duration, priority, goal_id).
- Gère `401`, `403`, `409`, `422`, `5xx`, timeout, JSON invalide, `proposal=null`,
  `agent_status != ok` avec états explicites. Aucun retry aveugle.
